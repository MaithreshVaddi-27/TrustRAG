# PHASE 1 — CRITICAL

`C-1` … `C-9`. Everything here was fixed in this pass unless marked otherwise.

### ✅ FIXED — C-1 · The global rate limit was completely inert

`apps/api/app/main.py:527` created a `Limiter` with `default_limits=["60/minute"]`
and stored it on `app.state`, but **`SlowAPIMiddleware` was never imported or
registered**. slowapi only consults `default_limits` from
`SlowAPIMiddleware.dispatch` or an explicit `@limiter.limit` decorator. Only
`/auth/register` (3/h) and `/auth/login` (5/min) were decorated — and on a
*second* `Limiter` instance, so counters did not even share storage.

Consequence: `POST /api/v1/analyses` — a full retrieval + LLM + verification
pipeline — was **unbounded**, as were upload, `/metrics`, `/health`. This
contradicts threat-model control **T-04** and prior-audit item **P1-19** (marked
"fixed").

Fix: register `SlowAPIMiddleware` and import it. Verified by reproduction —
60 requests now allowed, the 61st returns 429.

### ✅ FIXED — C-2 · The ABSTAINED path bypassed the grounding gate

`apps/api/app/services/analysis_service.py:711` stored the model's raw prose
whenever the verdict was `ABSTAINED` and the answer was not the bare token
`"ABSTAIN"`. The `else` branch routes every other verdict through
`_presentable_answer()`; this one re-decided for itself, so a hedged-but-
unverified answer reached the UI next to a reliability badge that said the
opposite. It also skipped `strip_citation_markers` and the `_looks_like_
scaffold_echo` guard, both of which live only in the `else` branch. Coverage on
those lines was 0%.

Fix: route ABSTAINED through the same single gate.

### ✅ FIXED — C-3 · CI was permanently red — `compose-smoke` could never pass

`docker-compose.yml:79` declared `env_file: - .env`. `.env` is gitignored and
untracked, and no CI step creates it, so `docker compose config` — the *first*
step of the `compose-smoke` job (`ci.yml:421`) — exited 1 on every clean
checkout, which fails `ci-gate` (`ci.yml:464`). Reproduced directly:

```
$ git archive HEAD | tar -x -C $TMP && cd $TMP && docker compose config --quiet
env file $TMP/.env not found: no such file or directory
EXIT=1
```

A gate that is always red cannot distinguish a real regression from the
baseline. This is the same failure class as P1-15, which the prior pass *did*
catch — the audit validated that the job existed, not that it ran.

Fix: `env_file: [{path: .env, required: false}]`, so a `.env`-less checkout
validates and a real deployment still supplies its own.

### ✅ FIXED — C-4 · The image healthcheck probed the always-200 endpoint

`apps/api/Dockerfile:92` targeted `/api/v1/health`, which by its own docstring
(`health.py:45`) "always returns 200 so monitoring tools can always receive a
response". Compose was overridden to `/health/ready` (P1-17), but **every other
deploy target — Render, Cloud Run, Kubernetes — uses the Dockerfile line** and
reported healthy while Mongo and Qdrant were down.

Fix: probe `/api/v1/health/ready` (503 when degraded).

### ✅ FIXED — C-5 · Blocking `subprocess` probes ran on the event loop

`get_cached_hardware_profile()` shells out synchronously on a cache miss
(`hardware.py:136` `nvidia-smi`, `:158` `nvidia-smi --query-gpu`, `:208`
`vm_stat`, each `timeout=5`). Three `async def` request handlers called it
directly: `health.py:123`, `models.py:52` (via `_safe_hardware_profile`), and
`models.py:155`. TTL is 300 s, so **every fifth minute the whole worker froze
for up to ~10-15 s** — stalling every in-flight request, every SSE heartbeat
(a dropped proxy connection presents to the user as a hung/failed analysis), and
every running analysis. `main.py:252` already wrapped the identical call in
`asyncio.to_thread` for startup warmup, proving the pattern was known.

Those three functions also have **0% test coverage** (`hardware.py:135-169`).

Fix: `await asyncio.to_thread(...)` at all three sites.

### ✅ FIXED — C-6 · The cross-encoder's verdict never reached the prompt

`apps/api/app/rag/generation/generator.py:628` ordered evidence by
`rrf_score` **before** `rerank_score`. `rrf_score` is present on every fused row
and is never cleared, so the `rerank_score` branch was unreachable on the main
path. Two losses:

1. `Segment 1..N` numbering was fusion order, not relevance order — a small
   local model read its best passage last, in an 8192-token window.
2. The character-budget loop (`generator.py:698`) breaks on the highest-RRF
   tail, so a chunk the cross-encoder scored best but fusion ranked 8th was
   **cut from the prompt entirely**. The reranker could choose the candidate set
   but never the order or the cut.

Verified by execution: a chunk with `rrf=0.0328, rerank=-9.0` sorted ahead of
`rrf=0.0164, rerank=11.0`. The same precedence bug in
`reranker.py:_is_high_confidence` made its `rerank_score >= 0.80` and
`dense_score >= 0.78` branches dead on every hybrid row.

Fix: precedence is now `rerank_score → rrf_score → dense_score` in both places.
**This is the single highest-leverage fix for local-model answer quality** —
every claim the verifier produces was conditioned on evidence the cross-encoder
never got to prioritize.

### ✅ FIXED — C-7 · Per-email login lockout never engaged

`auth_service.py` counted failures only under `email|ip`. `_is_locked_out` then
fell back to looking up the bare `email` key — which nothing ever wrote, so the
fallback was dead code and the account-level lockout never fired. Spraying one
known victim email from N addresses gave N independent counters, each below
threshold, at N × the per-IP rate limit; the exponential escalation applied
per-pair and never to the victim.

Fix: record and check **both** the `(email, ip)` pair and an email-only aggregate.

### ✅ FIXED — C-8 · Two sequential Mongo round-trips on every authenticated request

`api/deps.py` awaited the revocation lookup, then the user lookup — two
independent queries on different collections, serialized, on *every* authed
endpoint. With the UI polling analyses at 5 s and claims/conflicts/KBs/health/
providers on top, one idle dashboard tab spent ~10 serialized RTTs/min on
authentication alone.

Fix: `asyncio.gather` both; revocation is still evaluated first so a revoked
token never uses the fetched document. (A test pinned the old ordering; the
security property is preserved.)

### 🔴 OPEN — C-9 · `qa_contract` / eval claims have no producer (claims, not code)

`apps/web/src/components/landing/landingData.js:186-215` publishes
`99.4%` vs `81.2 / 68.7 / 24.1%` accuracy under the heading **"EMPIRICAL
BENCHMARKS & EVALUATION"**, and `HeroSection.jsx:21` renders `99.4% Claim
Precision` inside a card with an `animate-ping` live dot. Prior-audit **T-6**
confirms the eval harness has no runner, so nothing in this repository can
produce those numbers. Two tells that they are filler: the `speed` chart gives
`text-emb-3-large` and `Gemini-Embedding-001` an identical `1228 MB`, and
`landingData.js:242` asserts *"Eliminates 92% of transient retrieval failures"*
while `:260` asserts *"Guarantees that evidence cited is mathematically genuine
and legally active"* — absolute guarantees on a security product.

Prior-audit P1-24 removed hardcoded superlatives from `src/pages` and
`src/components/workbench` but never read `src/components/landing/`, so the
class survived on the first page any prospect sees.

Fix (needs a decision, not a patch): wire a real eval runner and print its
provenance, **or** delete the section. Not fixed here — shipping invented
accuracy numbers in either direction is a product call.

# PHASE 2 — NEEDED

### ✅ FIXED — N-1 · Terse correct local answers were converted to refusals

`generator.py:strip_stray_abstain` applied a `len(text) < 20 → "ABSTAIN"` floor
**unconditionally**, so a correct small-model answer like `"30 days."` or
`"60/min."` became a refusal → `ABSTAINED` → score 0. Verified by execution
before the fix.

The floor's intent was "nothing substantive remains after peeling a stray
ABSTAIN token". Fix: apply it only when a token was actually peeled, and treat a
**leading** bare `ABSTAIN` as a refusal outright (`"ABSTAIN\nsee above"`).

### ✅ FIXED — N-2 · The refusal gate fired on any hedge anywhere in a correct answer

`verdict.py:is_refusal_answer` matched 10 broad substring regexes against the
whole answer. `insufficient (evidence|…)` and `cannot (verify|…)` routinely appear
in *trailing clauses of grounded answers*:

| Answer | Before | After |
|---|---|---|
| `"The leave limit is 30 days. Note there is insufficient evidence about exceptions."` | refusal ❌ | not a refusal ✅ |
| `"Employees accrue 1.5 days per month. [Segment 1]"` | not a refusal ✅ | not a refusal ✅ |
| `"I couldn't verify this."` | refusal ✅ | refusal ✅ |
| `insufficient evidence` | refusal ✅ | refusal ✅ |

This is **the primary cause of "the model is not reliable"**: the better-hedged a
local model wrote, the more reliably it was marked unreliable. Fix: the refusal
must **lead** (appear in the first sentence), or removing every refusal phrase
must leave nothing to assert.

### ✅ FIXED — N-3 · An empty knowledge base was reported as an unverifiable answer

`graph.py:611-622` detects "0 indexed chunks", authors an actionable message
("Please upload a document…") and sets `verdict_status = "PASS"` so recovery
doesn't burn budget re-searching an empty index. `analysis_service.py` never read
that field; `verdict_from_state` saw `claims=[]` and recomputed
`FAIL / "No claims extracted for verification"`, **overwriting the authored
message**. The user was told to "add documents covering this topic" for a KB
that has none.

Fix: honour the graph's terminal `PASS` when it passed for a reason claim counts
cannot express (no claims, no chunks, non-refusal answer).

### ✅ FIXED — N-4 · Frontend blank-screen crash on blocked storage

`authStore.js:51` read `localStorage.getItem` at module scope **unguarded**,
while every other access in the file was wrapped. `getItem` throws
`SecurityError` when storage is blocked (Safari Private Browsing, hardened
enterprise profiles, embedded webviews) — that escapes module evaluation before
`main.jsx` renders, so the app became a blank white page that **no error boundary
can catch**. Fix: a guarded `readToken()`.

### ✅ FIXED — N-5 · The Playground submitted a model the server probably didn't have

`PlaygroundPage.jsx:82` guarded with `if (!selectedModel && activeProviderDefault)`
— but both initialisers are non-empty, so the branch could never fire. Nothing
ever reconciled `selectedModel` with the server's model list. On a fresh install
serving a different GGUF the `<select>` value matched no `<option>` (blank box)
while `handleSubmit` posted the stale id anyway. Fix: reconcile whenever the
model list changes and the current selection is not in it.

### ✅ FIXED — N-6 · A null reliability score was plotted as 100% and labelled TRUSTED

`DashboardPage.jsx:194` substituted `status === 'completed' ? 100 : 0` for a
missing score, so the Reliability Progression Curve pinned a point to the top
gridline with a `TRUSTED` tooltip while `ReliabilityBadge` rendered `—` for the
same row. The same fallback also relabelled `abstained` as `FAILED`. Fix: pass
`null` through so the chart leaves a gap.

### ✅ FIXED — N-7 · The simulation asserted two contradictory scores at once

`SimulationSandbox.jsx:105` hardcoded `GROUNDED: 96.4%` directly above
`Post-Healing Score: 98.4%` (rendered from the scenario data 100 px below), with
`simStep` initialised to `4` so it painted on first load. Fix: derive from
`currentScenario.recovery.finalScore`.

### 🔴 OPEN — N-8 · Per-analysis claims/evidence/trace reads are unbounded

`analysis_service.py:475`, `:495`, `:512` — none of `_fetch_claims`,
`_fetch_evidence`, `_fetch_trace` applies a `.limit()`; each drains a cursor
into a Python list, and `get_analysis_detail` gathers all three. Trace grows
with every pipeline step *and* every recovery round (30-day TTL). The prior
audit capped the cross-analysis list endpoints but missed these three, which the
frontend finalize path hits on every completion.

Fix: `limit`/`skip` on `/claims`, `/evidence`, `/trace` (`Query(le=500)`) and cap
the fetchers.

### 🔴 OPEN — N-9 · `/conflicts` silently returns empty pages past the first 100

`analysis_service.py:976` — `per_source = min(skip + limit, 100)`. With
`limit <= 100` and more than 100 conflicts, `skip=200` fetches only the 100
newest per source, sorts, then `conflicts[200:300]` returns `[]` — the UI shows
"no conflicts" while hundreds exist. Prior-audit N-34 is accurate about
merge→sort→paginate but the 100 cap makes it wrong past page 1.

### 🔴 OPEN — N-10 · The cloud spend cap reads the global provider, not the request's

`llm/llm_ledger.py:80` checks `get_model_config().llm_provider`. The checked-in
default is `llama_cpp`, and the effective provider is resolved per-request
(`analysis_service.py:359` → `graph.py:1556`), so a user who selects Gemini
gets `max_calls_per_analysis() → None` — the spend guard is inert for the only
path that reaches a cloud model. The inverse also fires: a global `gemini`
default throttles local runs, contradicting the function's own docstring. Zero
tokens are recorded for structured-output calls (`llm_ledger.py:176` probes
`usage_metadata`/`response_metadata`/`.content`, none of which exist on the
returned Pydantic model), so the ledger under-reports the verification tree.

Fix: thread the effective provider into `begin_analysis()` and key the cap off it;
recover usage from the underlying `ChatResult`.

### 🔴 OPEN — N-11 · MCP `trustrag_search` returns `chunk_id: "None"` for every result

`mcp/server.py:251` — `reciprocal_rank_fusion` builds rows with `id`, not
`chunk_id`, and never populates `zone`, so `str(None)` → `"None"` and the
index-time zone boost is lost on every result. Line 250 uses `or` for the score,
so a genuine cross-encoder logit of exactly `0.0` is silently replaced by the RRF
score — and on this path the two live on incomparable scales (logit ≈ ±11 vs RRF
≈ 0.016-0.033).

### 🔴 OPEN — N-12 · MCP `trustrag_verify_claim` returns unmappable segment numbers

`mcp/server.py:258` — `format_context` deduplicates by a 20-word prefix and drops
trailing segments at the tier char budget, so the returned
`supporting_segments` index into the *deduped, truncated* context. The tool
returns no `chunk_indices`, so a client doing `evidence_texts[N-1]` links a claim
to the wrong evidence, silently. The verifier itself guards this on every other
path (`verifier.py:1327`, `:1450`) via `format_context_with_chunk_indices`.

### 🔴 OPEN — N-13 · Structured-output repair is untested and can return the wrong object

`llm/llm_utils.py:158-161` — the fallback iterates `data.values()` and returns the
**first** dict-shaped value, with `suppress(Exception)` swallowing mismatches. A
response `{"decomposition": {...}, "evidence": {...}}` whose schema matches the
second key returns the wrong value with **no error**. This parser sits between
every LLM response and claim extraction. `llm_utils.py` is at **21% coverage
with lines 100-166 entirely uncovered**.

### 🔴 OPEN — N-14 · The coverage gate is in `addopts`, breaking local test runs

`pyproject.toml:148` puts `--cov-fail-under=78` in `addopts`, so *every* pytest
invocation is gated — including single-test runs and every IDE test runner:

```
$ pytest tests/test_api_contract.py -k status_vocabulary
FAIL Required test coverage of 78% not reached. Total coverage: 24.18%
```

Fix: keep `--cov` in `addopts`, move `--cov-fail-under` to the CI step.

### 🔴 OPEN — N-15 · `npm install` in the CVE gate audits a different tree than CI ships

`.github/workflows/security.yml:82` — every build job uses `npm ci`; this job
uses `npm install`, which can re-resolve the lockfile. This is the exact defect
the prior audit fixed on the Python side (N-95) and never applied to Node.

### 🔴 OPEN — N-16 · `list_kbs` truncation warning is dead code for any limit < 500

`kb_service.py:121` — the guard is `len(kbs_raw) == 500`, but the endpoint caps
`limit` at 500 with a default of 200, so the branch never fires. A user with 600
KBs silently loses 400 with no log line. Prior-audit N-36 claims this "logs the
500-row truncation"; the log half does not work.

### 🔴 OPEN — N-17 · A trace-write failure orphans the analysis in `pending` forever

`analysis_service.py:406-416` — `add_trace_event` is awaited *after* the analysis
row is inserted and *before* `background_tasks.add_task`. A Mongo blip raises,
the request 500s, and the row sits at `status: "pending"` with no pipeline ever
scheduled. The startup reaper (`main.py:206`) only matches `"processing"`.

### 🔴 OPEN — L-7 · Retry with no backoff, no jitter, and a fresh HTTP client per attempt

`llm/local_llm.py:626-632` — `AsyncClient` is constructed *inside* the retry loop

### 🔴 OPEN — L-8 · Deployment docs state the wrong default for the reranker

`docs/deployment/README.md:311` — the incident kill-switch table says
`reranker.enabled: false (default)`; `config/models.yaml:113` says
`enabled: true`. An operator mid-incident reads "default: off", concludes the
cross-encoder is not burning CPU, and does not flip the one switch that would.
The same file still tells operators to copy a model into the `model_cache`
volume that P1-16 deleted, and pins "381 backend tests green" against an actual
697→721.

### 🔴 OPEN — L-9 · Unparameterised metric label cardinality on an unauthenticated endpoint

`core/observability/metrics.py:42-43` normalises only 24-hex and all-digit path
segments. `tracing_middleware` records **every** request including 404s, and
`/api/v1/metrics` is unauthenticated — so any probed path shape permanently
allocates a new key. `_norm_path` is also exposition-format injectable: a path
containing `"` emits a broken Prometheus series.

### 🔴 OPEN — L-10 · Source-regex assertions guard contracts that behavioural tests should guard

`tests/test_api_contract.py:381-398` regexes `"status":\s*"([a-z_]+)"` out of the
service source. It has teeth (non-empty match set, required members pinned) but
is coupled to literal formatting — hoisting the statuses to constants silently
changes what it sees. `tests/test_sse_outage.py:24-85` shows the correct
pattern: source check **plus** a real behavioural test. At least six tests use
`inspect.getsource` on the unit under test.

### 🔴 OPEN — L-11 · Real wall-clock sleeps in the suite

`tests/test_search_mcp.py:205` `time.sleep(1.0)`;
`tests/test_upgrade_phases.py:65` `await asyncio.sleep(5)`. ~6 s of a 24 s suite
(25%), and both are flake vectors on a loaded runner.

### 🔴 OPEN — L-12 · A k6 check that cannot fail

`load-test/smoke.js` — `'analyses returns 200 or 404'` passes when the endpoint
works *and* when it 404s, contributing a green check to a billed load gate.

### 🔴 OPEN — L-13 · MCP skips the token revocation denylist

`mcp/server.py:189` `_require_service_token` calls `decode_service_token` only,
whereas `api/deps.py:103` also consults the denylist. Service tokens live 24 h,
so a revoked-but-unexpired token still grants `trustrag_search` / `trustrag_list_kbs`
/ `local_llm_chat`. Reachability is limited because the stdio server is local.

### 🔴 OPEN — L-14 · Frontend coverage is unmeasured and unthresholded

`vitest.config.js` has no `coverage` block and no threshold, so deleting a test
is invisible. `npm test` also requires Node 22 (host has 20), so the frontend
unit suite is currently **not runnable** — "lint clean, build OK" does not imply
tests pass.
